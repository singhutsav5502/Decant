  32-bit commit-limit behavior identical (2048/3072 FAILED, as expected for LAA).
- Both runtimes: repro-gate (setjmp/longjmp + wndproc + VirtualAlloc) completes.
- Swap runtime: CrossOver's wow64cpu engaged (brand=VirtualApple, AVX2/BMI1 handled).
- The synthetic tests do NOT reproduce the installer's hard fault on stock staging,
  so the fault is conditional on installer-specific context (likely the GUI thread's

  far-jump/iretq difference moot there — but is NOT yet proof that the far-jump is the
  crash's root cause, because the trigger path wasn't forced differentially here.

## Conclusion so far

The synthetic gate stress does NOT reproduce a hard fault on stock staging nor on the
fx runtime; both complete all phases with only intentional exceptions. Therefore the
"far-jump vs iretq" discrimination via this test program has not yet shown a crash on
stock staging. The installer-context dependency remains the leading explanation for the
original c0000005 in syscall_32to64 on stock staging.

## DECISIVE RESULT (2026-11-04, ~21:20-22:15) — installer run under fx runtime

Ran the real installer in bottle vol-cxgate (runtime staging-11.21-cxgate = staging 11.21
with CrossOver's wow64cpu.dll swapped in; WINEDEBUG=+seh,+loaddll,+thread,+process).

- User clicked Install; extraction progressed (bzip3 at ~857% CPU), was NOT frozen
  (setup.tmp at ~2% CPU), and the install COMPLETED: process exited cleanly ~22:0x,
  log 20261104-220221-29187.log ended with normal module unloads (unarc.dll, ISDone.dll,
  innocallback.dll, idp.dll) and no crash.

- Compare: the same installer under STOCK staging froze earlier at ~34MB / 11 files in
  the worker (VirtualAlloc halving probe loop → infinite size-0 loop).

## Updated conclusion

- Synthetic tests (memprobe, repro-gate, repro-gate2) did NOT crash on either build.
- Real installer: fx runtime → COMPLETED; stock staging → FROZE.
- This does not by itself prove the retfq/far-jump is the root cause, but it is the first
  clean, real-world, real-installer data point in this investigation that the swapped
  wow64cpu (CrossOver) is protective and stock is not — strongly supporting the far-jump
  hypothesis for Report 1, and making the swap a viable local workaround to test
  (full completion of extraction = workaround works for the freeze path).
